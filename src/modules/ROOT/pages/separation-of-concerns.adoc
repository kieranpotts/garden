= Separation of concerns

// 📝 DRAFT

:link-dijkstra-ewd447: https://www.cs.utexas.edu/~EWD/transcriptions/EWD04xx/EWD447.html
:link-parnas: https://doi.org/10.1145/361598.361623
:link-tarr: https://doi.org/10.1145/302405.302457

Separation of concerns is a xref:design-principle.adoc[*design principle*] that asks a system to be organized so that each element addresses one distinct concern, and each concern is addressed by as few elements as possible.

A *concern* is anything the system must do or account for: a feature, a policy, a responsibility, or a xref:quality-attribute.adoc[*quality attribute*] such as security or performance.

The principle is attributed to Edsger Dijkstra, who described it in 1974 as "the art of... letting one aspect predominate over the others" by focusing on each in turn. In the same essay he called it, "even if not perfectly possible," the only available technique he knew of for effective ordering of one's thoughts.

The principle is broader than any one method. It names an instinct — that a reader, tester, or maintainer should be able to reason about one concern without holding the rest of the system in mind — rather than a particular mechanism. The mechanisms that realize it are the techniques of xref:decomposition.adoc[*decomposition*] and xref:modular-design.adoc[*modular design*] — breaking the system into parts, giving each part a cohesive set of responsibilities, and exposing only a narrow xref:interface.adoc[*interface*] to the rest. What keeps the boundary honest is xref:encapsulation.adoc[*encapsulation*] (information hiding), and the broader discipline that makes the boundary possible is xref:abstraction.adoc[*abstraction*].

A system that separates concerns well tends to be both highly xref:cohesion.adoc[*cohesive*] within each part, and loosely xref:coupling.adoc[*coupled*] between parts. The two are the same boundary seen from opposite sides. A module that owns a single concern has fewer reasons to reach outside itself, and so drags fewer neighbors along when it changes. The active work of keeping that coupling low is xref:decoupling.adoc[*decoupling*].

The principle is general enough to appear under several specialized names. The xref:single-responsibility-principle.adoc[*single responsibility principle*] is separation of concerns narrowed to the unit of a single class or module, and reframed around the *actor* whose interests the module serves. At the method level, xref:command-query-separation.adoc[*command query separation*] separates the concern of mutating state from the concern of observing it.

At the scale of a whole application, the principle is the organizing idea behind xref:layered-architecture.adoc[*layered architecture*], which stacks presentation, business, and persistence concerns into distinct layers, and behind xref:hexagonal-architecture.adoc[*hexagonal architecture*] and xref:clean-architecture.adoc[*clean architecture*], which isolate the domain from the infrastructure that delivers and persists data. The same instinct, applied to operating systems and command-line tools, is one of the tenets of the xref:unix-philosophy.adoc[*Unix philosophy*] — that each program does one thing well, and programs are combined to address larger concerns.

Not every concern can be assigned to a single module. A xref:cross-cutting-concern.adoc[*cross-cutting concern*] — logging, security, transaction management — cuts across many modules that each have a different primary responsibility. Separation of concerns still applies, but the technique changes. The concern is factored out into a *middleware* pipeline, an *aspect*, or an infrastructure layer rather than localized in one module. The principle is the same, only the shape of the boundary differs.

== Dimensions of separation

A system can be divided along more than one axis, and each axis separates a different kind of concern.

* *By layer*: presentation, business logic, and persistence, as in a layered architecture.

* *By feature or domain area*: billing, ordering, and shipping each own their own logic, as in a modular monolith or a bounded-context-per-service design.

* *By technology*: structure, style, and behavior in a web page are kept in separate languages (HTML, CSS, JavaScript), so each can change without disturbing the others.

* *By time or lifecycle*: configuration is separated from code, and build time from run time, because the concerns change on different schedules.

* *By policy and mechanism*: what the system decides is separated from how it carries the decision out, so that either can be replaced.

== Tangling and scattering

When separation fails, it fails in one of two ways. Concerns are *tangled* when one module mixes several of them, so that the code for each is interleaved with the others. Concerns are *scattered* when one concern is spread across many modules, so that no single place implements it. The two usually come together, and both are signs of a boundary drawn in the wrong place.

A classic tangle is logic that has drifted into the entry-point layer of an application, as in the xref:fat-controller.adoc[*fat controller*] and its more general form, the xref:smart-ui.adoc[*smart UI*]. Scattering shows up when a single change forces edits in many modules, which Martin Fowler's catalog of xref:code-smell.adoc[*code smells*] calls xref:shotgun-surgery.adoc[*shotgun surgery*], or when one module must be edited for unrelated reasons, which he calls xref:divergent-change.adoc[*divergent change*]. A codebase where tangling and scattering are everywhere is, in the limit, a xref:big-ball-of-mud.adoc[*big ball of mud*].

== The tyranny of the dominant decomposition

David Parnas argued in 1972 that a system should be divided according to the design decisions most likely to change, each hidden inside a module, and not according to the steps of its processing flow. That remains the most practical guide to where to draw a boundary.

But any one decomposition favors a single dimension, and the concerns on the other dimensions are forced to cut across it. Tarr and colleagues named this the "tyranny of the dominant decomposition" in 1999. If code is divided by feature, then layer-like concerns such as logging or security are scattered across every feature, and the reverse is true if it is divided by layer. This is the problem that the cross-cutting concern techniques address, and which motivated aspect-oriented programming.

== Trade-offs

Pursued without judgment, separation of concerns becomes its own problem. Splitting a feature across many modules to keep each "pure" scatters a single thread of logic across the codebase, and the reader must follow that thread through a chain of indirections to understand what the feature does. This is the *locality of behavior* critique. Code that does one thing is easier to reason about when the doing of it lives in one place.

The xref:grug-brained-developer.adoc[*grug-brained developer*] makes the same point more bluntly, warning that excessive separation spreads a feature across so many files that neither the feature nor its boundaries are easy to see.

The aim, then, is not to maximize the number of modules but to draw boundaries that align with distinct concerns and likely axes of change. A concern is worth separating when it changes at a different rate, or for different reasons, than its neighbors.
