= N+1 query problem

The N+1 query problem is a performance defect in which an application issues one query to fetch a list of N parent records, and then N further queries, one per parent, to fetch each parent's related child records. Instead of two queries, or one join, the application makes N+1 round trips to the xref:database.adoc[*database*].

In application code, the defect usually takes the form of a simple loop over a collection, with a single database fetch taking place in each iteration of the loop. Fetching 100 users (one query) and then each user's posts (one query per user) requires 101 individual database reads. The defect is even easier to introduce, and harder to spot, when an *object-relational mapper (ORM)* uses xref:lazy-loading.adoc[*lazy loading*] to return the parent record with their associations left as unloaded placeholders. The inner queries are hidden behind an innocent-looking property access. xref:graphql.adoc[*GraphQL*] resolvers have the same issue.

Because the defect is silent, it is best caught mechanically. Query counts can be asserted in tests, logged per request, or surfaced by an ORM's query logger or by xref:application-performance-management.adoc[*application performance monitoring*]. A request whose query count scales with the size of its result is the signature of the N+1 problem.

All remedies require replacing the per-row queries with a bounded number of set-based queries.

* *Eager loading with a join.* Fetch the parents and children together in a single query with a `JOIN`. Most ORMs expose this as a query option, eg. `.includes()` in Rails.

* *Eager loading with a batch query.* Fetch the parents, then fetch all the related children in one second query using an `IN` clause over the parent identifiers. Stitch the results together in memory. Rails's `.preload()` work this way.

* *Batching.* Collect the individual lookups and issue them as a single batched query. This is the standard remedy for GraphQL resolvers.
