= N+1 redundancy

N+1 redundancy is a sizing rule for xref:redundancy.adoc[*redundancy*] in which a system is provisioned with N components, the number needed to carry the workload at full capacity, plus one spare. If any single component fails, the remaining N can still carry the full load.

For example, a web application that needs three servers to handle peak traffic is deployed on four. If one server fails, the other three continue to serve at 100% of required capacity.

The appeal of N+1 is its cost, because the spare's overhead shrinks as N grows. One spare in four is a 25% overhead, but one in twenty is only 5%.

The trade-off is that the system tolerates only a single failure at peak traffic. A second failure, before recovery of the first, leaves the system short of capacity.

Furthermore, the spare does not protect against *common-mode failures* that affect every component at once.

N+1 is most common in data center infrastructure, eg. power supplies, cooling units, and network links, and in fleets of identical stateless servers behind a xref:load-balancing.adoc[*load balancer*].

== Alternative patterns

* *N+M.* Keep M spares for N working components, so that M concurrent failures are tolerated. It is used where repair times are long, or where failures are likely to cluster.

* *2N.* Duplicate every component or path, so that a complete, independent mirror of the system stands ready. It tolerates the loss of an entire side, but at double the cost.

* *2N+1.* A 2N system with an additional spare, so that the system keeps full redundancy even after one side's component has failed.
