= Replication

// TODO: https://redis.io/blog/what-is-data-replication/

Replication, also known as *xref:redundancy.adoc[data redundancy]*, is the
process of creating and maintaining identical copies of data across multiple
servers or nodes. In cloud platforms, replicas are commonly spread across
*xref:availability-zone.adoc[availability zones]* to survive data-center-level
failures.

Together with *xref:sharding.adoc[sharding]*, replication is a key technique for
scaling databases, and a core technique of
xref:distributed-databases.adoc[*distributed databases*]. Sharding splits data
across multiple servers, while replication duplicates data across multiple
servers. The two together are what make
xref:nosql-databases.adoc[*NoSQL databases*] horizontally scalable and
fault-tolerant, allowing a cluster to grow in capacity and survive node loss
without an outage.

Data replication becomes necessary the more that data is distributed across
multiple servers, for example in
*xref:service-oriented-architecture.adoc[service-oriented]* or
*xref:microservices.adoc[microservices]* architectures.

In a *xref:monolith.adoc[monolithic]* architecture, data is typically stored in
a single database instance, and joins are typically used to query relational
data across multiple tables.

image::monolith-with-cross-table-joins.svg[]

But in a *xref:distributed-system.adoc[distributed software]*, those joins turn
into network calls. This increases *xref:latency.adoc[latency]*, decreasing
*xref:performance.adoc[performance]* and having implications for the
*xref:fault-tolerance.adoc[resilience]* of the system.

image::microservices-with-cross-service-calls.svg[]

Data replication is one possible solution to these problems. Simply, data is
replicated to wherever it is needed, so that discrete services are less reliant
upon each other. Services therefore work faster by needing to use only local
data.

Besides the *xref:performance.adoc[performance]* benefits of reducing network
calls, data replication also improves the
*xref:fault-tolerance.adoc[fault tolerance]* and
*xref:availability.adoc[availability]* of
*xref:distributed-system.adoc[distributed software]*, due to reduced
dependencies between services.

Data replication also creates the foundation for
*xref:failover.adoc[failover]* and
*xref:disaster-recovery.adoc[*disaster recovery*]: a replica is a live copy that can take over instantly when the primary fails, rather than requiring you to restore from a backup.

When planning replication, consider two key metrics:

* *Recovery Point Objective (RPO).* The amount of data loss acceptable during a failure, measured as the oldest unreplicated change. Asynchronous replication with short lag gives low RPO; synchronous replication gives RPO = 0.
* *Recovery Time Objective (RTO).* The maximum acceptable downtime after a failure, measured from detection to service restoration. Replicas enable fast failover, but a standby that hasn't kept pace with replication will reject writes during promotion.

Trade-offs are made in terms of *xref:consistency.adoc[data consistency]*, the increased system *xref:complexity.adoc[complexity]* required to manage the data replication and synchronization processes, and storage costs. Storage costs scale with the number and size of replicas, so partial replication that caches only hot or localized data can reduce requirements.

Data synchronization can be achieved using either batch processes or
*xref:event-stream.adoc[event streams]*. Some database systems also provide
built-in support for data replication across multiple nodes.

*Change data capture (xref:change-data-capture.adoc[CDC])* is the most common
technique for streaming replication. CDC monitors the database's transaction log
and emits structured events for each change (INSERT, UPDATE, DELETE), preserving
event order and minimizing impact on the primary. This technique underlies
*xref:active-active.adoc[Active-Active Geo Distribution]* and multi-region
replication patterns.

Leadership models determine the replication topology:

* *Single-leader replication:* One node handles all writes. Changes propagate asynchronously to one or more read replicas. This is the simplest model, works well for read-heavy workloads, but introduces a single point of failure and writes go through a bottleneck.
* *Multi-leader replication:* Multiple nodes accept writes concurrently. Each node replicates its changes to others. This provides high availability across regions and reduced write latency for local users, but requires conflict resolution.
* *Leaderless replication:* Clients write directly to multiple nodes, and consistency is managed via *quorum reads/writes*. Popular in distributed databases like Cassandra and Dynamo.

Replication timing introduces another trade-off:

* *Synchronous replication:* The primary waits for confirmation that a write has been acknowledged and applied before responding to the client. This ensures strong consistency and RPO = 0, but adds round-trip latency to every write. Best for in-region deployments where network latency is low.
* *Asynchronous replication:* The primary acknowledges the write immediately and propagates changes to replicas afterward. This eliminates write latency, but introduces *replication lag* — a window where replicas may be stale. In the worst case, a primary failure during this window can result in data loss, so the system must size replicas to handle the lag window.

Many production systems use a hybrid approach: synchronous replication within a region for critical data, and asynchronous replication across regions for everything else.

Conflict resolution is required when multiple nodes accept writes. Common strategies include:

* *Last-write-wins:* Uses timestamps or sequence numbers to choose the most recent update.
* *Version vectors:* Track the causality history of updates and merge deterministically.
* *Application-level merge logic:* Custom business rules that resolve conflicts based on domain-specific needs.

*Conflict-free replicated data types (CRDTs)* provide a mathematical guarantee of eventual convergence without explicit conflict resolution by using data structures that merge automatically. CRDTs are particularly useful in leaderless and multi-leader scenarios where avoiding conflicts at the data model level is desirable.

Finally, data need not be replicated in the form of its
*xref:single-source-of-truth.adoc[source of truth]*.
*xref:materialized-view.adoc[Materialized views]* can be used to store
pre-processed data that's optimized for specific use cases, such as reporting.
