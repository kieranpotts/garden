An *agent*, or *AI agent*, is a xref:large-language-model.adoc[*large language model*] that pursues a goal by calling tools in a loop, deciding for itself which action to take next and when the job is done. Software built around agents is described as *agentic*.

Simon Willison's one-line definition, "an LLM agent runs tools in a loop to achieve a goal", has become a common reference point. The goal is what makes the loop finite. The agent stops when it judges the goal met, or when a limit stops it.

== Definitions

The term "agent" predates large language models. In AI research, Russell and Norvig define an agent as anything that perceives its environment through sensors and acts on it through actuators. In software engineering, a *software agent* is a program that acts on behalf of a user or another program, with some freedom to decide for itself what to do.

Wooldridge and Jennings identified four properties that set an agent apart from an ordinary program. An LLM agent fits each of them:

* *Autonomy*: An agent chooses its own next step, without a person directing each one.
* *Reactivity*: An agent perceives its environment, through the results of its tool calls, and responds to what it finds.
* *Proactiveness*: An agent takes the initiative in pursuit of its goal, planning and taking steps that nobody asked for individually.
* *Social ability*: An agent interacts with people and with other agents, as in a xref:multi-agent-system.adoc[*multi-agent system*] or over a protocol such as xref:agent2agent.adoc[*Agent2Agent (A2A)*].

LLM agents add a fifth property, *persistence*, which is keeping on toward a goal over many steps rather than running once and stopping. How long an agent can stay on track is a measure of its capability in its own right. METR found that the length of software tasks that frontier agents can complete with 50% reliability, measured by how long the tasks take a human expert, doubled roughly every seven months between 2019 and 2025.

The modern LLM agent descends from *ReAct*, a 2022 prompting technique in which a model interleaves reasoning with actions such as search queries, reading each action's result before its next thought. Function-calling APIs, and later xref:reasoning-model.adoc[*reasoning models*] that plan between tool calls, turned that prompting technique into the standard architecture.

== Model and harness

An agent is composed of a model and a harness.

----
agent = model + harness
----

The *model* is the underlying LLM. It is a reasoning engine, the "brain" that turns input tokens into output tokens. On its own, a model has no tools and no memory. It is executed by a xref:model-runtime.adoc[*model runtime*], and each run is an act of xref:inference.adoc[*inference*].

The xref:agent-harness.adoc[*harness*] is conventional software that wraps a model and turns it into an agent. It gives the model tools (file access, shell commands, web search, and so on), curates what goes into the model's context, enforces xref:guardrail.adoc[*guardrails*], saves sessions, and runs the xref:agent-loop.adoc[*agent loop*]. Curating the context is the work of xref:context-engineering.adoc[*context engineering*].

Different models bring different knowledge and capabilities, but it is the harness that shapes what an agent can do. Two agents powered by the same model but run in different harnesses behave very differently, because the harness, not the model, decides which tools the agent has and what it is allowed to do.

== Sessions, turns, and steps

An agent's work breaks down into three units.

----
session        One continuous conversation with an agent.
└── turn       One user message, plus all the work the agent does in reply.
    └── step   One request to the model, plus the tool call it asks for, if any.
----

Within a turn, the agent loop runs on its own. The harness sends the context to the model, which either asks for a tool to be run or answers the user. If it asks for a tool, the harness runs it, adds the result to the context, and asks the model again. The turn ends when the model answers without asking for a tool, usually because it judges the job done. A turn can be a single step that produces a one-sentence answer, or hundreds of steps and twenty minutes of work. The model mostly decides how long a turn runs, though the harness can cap it with a step limit or a budget, and the user can interrupt.

Models are xref:stateless.adoc[*stateless*], so the harness re-sends the whole session history on every step. Everything an agent appears to remember is that history. It accumulates in the model's xref:context-window.adoc[*context window*] until, near the limit, the harness can xref:context-compaction.adoc[*compact*] it, replacing older history with a shorter summary. The harness also saves each session as an xref:agent-transcript.adoc[*agent transcript*], which is what allows a past session to be resumed or reviewed later.

== Human oversight

The gaps between turns are where a person, or an automated process, can step in, check what the agent did, correct its course, and send the next message. How much of that a person does sets a spectrum of ways of working.

At one end, a person works xref:human-in-the-loop.adoc[*human-in-the-loop*], reviewing each turn and steering the next. This catches problems while they are cheap to fix, at the cost of throughput, and suits tasks that are ambiguous, irreversible, or hard to review. At the other end, the agent runs xref:away-from-keyboard.adoc[*away-from-keyboard (AFK)*], unattended across many turns or even sessions, and people judge the final output afterwards. This suits tasks that are well specified, low risk, and easy to check, such as bug fixes, features that follow established patterns, codebase migrations, and test generation.

Working AFK, a developer can run several agents in parallel, delegating goals and reviewing results, which is xref:agent-orchestration.adoc[*agent orchestration*]. Where the orchestrating role is itself played by an agent that spawns others, the result is a multi-agent system. Designing systems in which code rather than a person fills the gaps between turns is xref:loop-engineering.adoc[*loop engineering*]. The discipline of building production software with agents, inside systems of constraints, tests, and feedback loops, is xref:agentic-engineering.adoc[*agentic engineering*].

== Agents versus workflows

At its simplest, an agent is an LLM running in a loop with tools. What separates this from a fixed *workflow* is who controls the flow. In a workflow, deterministic code decides each step, and the LLM is a component inside a path that is fixed at design time. In an agent, the model decides the path at runtime, choosing which tool to call next, how many times, and when to stop.

Anthropic's guide to building agents names five common workflow patterns, in rising order of autonomy:

* *Prompt chaining*: A fixed sequence of model calls, each one processing the output of the last, with programmatic checks between them.
* *Routing*: A model classifies an input and dispatches it to a specialized prompt, model, or tool.
* *Parallelization*: Model calls run concurrently, either on independent sections of a task or as repeated attempts at the same task whose results are voted on.
* *Orchestrator-workers*: A central model breaks a task down at runtime and delegates the parts to worker calls, then combines their results.
* *Evaluator-optimizer*: One model generates a response and another critiques it, in a loop, until the response passes.

The two are ends of a spectrum, and most production systems sit somewhere along it. The trade-off is predictability against flexibility. A workflow is cheaper, faster, easier to test, and fails in ways you can anticipate. It suits tasks whose steps are known in advance. An agent copes with open-ended tasks where the steps cannot be enumerated beforehand, at the cost of higher latency and spend, variable run lengths, and failures that are harder to predict.

A good default, and the one Anthropic recommends, is to give an agentic system the least autonomy that solves the problem. Start with a single model call, move to a workflow when the steps are known, and reach for an agent only where the model genuinely needs to decide the steps. A common hybrid embeds an agent as one step inside an otherwise fixed workflow. Where such a workflow must survive failures across long-running steps, it runs on an xref:execution-orchestrator.adoc[*execution orchestrator*] or a xref:workflow-management-system.adoc[*workflow management system*].

== Risks and failure modes

Autonomy multiplies the ways a system can fail, because nobody checks each step before the next one builds on it.

* *Compounding errors*: Every step's output becomes context for the steps after it. A wrong call early in a run, such as a misread requirement or a hallucinated file path, can derail all the work that follows, and small per-step error rates multiply over long runs.

* *Loops that don't converge*: An agent can repeat a failing action without making progress, which is a xref:runaway-loop.adoc[*runaway loop*], or approve flawed work without noticing, which is a xref:nodding-loop.adoc[*nodding loop*].

* *Prompt injection*: Every tool result is text the model reads, so instructions planted in a web page, an email, or a file can hijack the agent. This is xref:prompt-injection.adoc[*prompt injection*]. Simon Willison calls the combination of access to private data, exposure to untrusted content, and the ability to communicate externally the *lethal trifecta*, because an agent with all three can be tricked into sending that data to an attacker.

* *Destructive actions*: An agent that can write can delete files, drop tables, or push to production as readily as it can read.

* *Cost*: Every step re-sends the whole context, so the token cost of a run grows faster than its length. xref:prompt-caching.adoc[*Prompt caching*] softens this, but does not remove it.

The defenses mostly live in the harness. They include least-privilege tools and permissions, xref:sandbox.adoc[*sandboxing*], guardrails, step and budget limits, and human approval for irreversible actions.

== Building agents

Building an agent means assembling six pieces. Frameworks and harnesses package them in different ways, but all six are present in any working agent.

* *Model*: The reasoning engine. Its capability sets the ceiling on how well the agent can plan, choose tools, and recover from errors, while its price and latency set the cost of every iteration of the loop. Agents often mix models, using a stronger one to plan and a cheaper one for routine steps.

* *Tools*: Functions the model can call, each described to the model by a name, a natural-language description, and a typed parameter schema, commonly expressed as xref:json-schema.adoc[*JSON Schema*]. The descriptions are prompts in their own right, and Anthropic argues that this *agent-computer interface* deserves as much design effort as a human-computer interface. The xref:model-context-protocol.adoc[*Model Context Protocol*] standardizes how tools are exposed to agents.

* *Instructions*: The system xref:prompt.adoc[*prompt*] and the policies that sit alongside it, covering the agent's role, the goal, the constraints, and what to do when stuck.

* *Memory and state*: The conversation so far, which is the agent's working memory and is bounded by the context window, plus any longer-term store that outlives a session. See xref:agent-memory.adoc[*agent memory*] and xref:agent-handoff.adoc[*agent handoff*].

* *Orchestration*: The loop itself, with the logic around it. This includes xref:retry.adoc[*retries*] for transient failures, validation of tool calls, xref:agent-hook.adoc[*hooks*] that run at fixed points in the loop, and stopping conditions such as a step limit or budget cap. Where several agents cooperate, this extends to agent orchestration.

* *Observability and evals*: The means of seeing what the agent did and judging whether it did it well. See xref:tracing.adoc[*tracing*] and xref:ai-eval.adoc[*evals*].

The last five pieces make up the harness. Designing and operating them is a discipline in its own right, known as harness engineering.

Few developers build a harness from scratch. Two kinds of tooling supply the pieces:

* *Agent development frameworks*: Code libraries and SDKs for writing agents.
* *Agent harnesses*: Ready-made runtime environments that execute agents, manage their lifecycle, control permissions, provide observability, and coordinate multi-agent workflows.

The line between the two blurs, since some frameworks include harness capabilities and some harnesses offer development tools. The distinction helps clarify whether you're looking for a tool to _write_ agents or an environment to _run_ them.

Frameworks differ mainly in how much control they give you over the flow. Some supply components and prebuilt agent constructors for a quick start. Others, such as LangGraph, model an agent as an explicit graph of nodes with persisted state, which gives control over branching, human approval, and long-running runs. Vendor SDKs, such as the OpenAI Agents SDK, the Claude Agent SDK, and Google's Agent Development Kit, ship the vendor's own agent loop with built-in tools.

Almost all frameworks lean on typed schemas, such as Pydantic models in Python or Zod schemas in TypeScript, to validate model output and tool arguments, since LLM output is unreliable text. When validation fails, the error can be fed back to the model so that it corrects itself.
