*Agentic systems* are xref:large-language-model.adoc[*LLM*]-based systems that can act autonomously to achieve goals. *Agents*, also known as *AI agents* and *software agents*, are a key component of many AI applications, from personal assistants to autonomous vehicles and software automation.

== Definitions

The term "agent" predates large language models. In computer science, a software agent is a program that acts on behalf of a user or another program with some degree of autonomy to decide for itself what to do.

What distinguishes an agent from an ordinary program — or from a single LLM inference call — is a cluster of properties.

* *Autonomy.* An agent reacts without constant human intervention, deciding its own next step.
* *Reactivity.* An agent perceives its environment and responds to it.
* *Proactivity.* An agent pursues goals on its own initiative, not only in response to a user prompt.
* *Persistence.* And agent runs in a xref:agent-loop.adoc[*loop*] toward a goal, rather than a one-off execution.

It helps to distinguish three closely related concepts.

* *Model.* The underlying LLM, a reasoning engine (the "brain") that transforms input tokens into output tokens. It has no persistent state, no tools, and no memory. A model is executed by a *model runtime* (or model engine) in a process known as *inference*.

* *Agent.* A model instance running within an active context, equipped with tools, a system prompt, and a conversation history. The agent is the model in operation via a harness.

* *Harness.* The infrastructure layer that creates and manages agents. It provides the tools the agent can use (file system access, shell execution, web search, etc.), manages the context window, enforces guardrails, handles memory persistence, and orchestrates multi-step task execution.

----
agent = model + harness
----

The harness shapes what an agent can do. At its simplest, an agent is an LLM running in a loop with tools. Given a goal and the context so far, the model decides whether to answer or to call a tool — eg. query a database, call an API, or execute some code. The harness captures the result of the tool call, adds it to the context, and the model infers again with the updated context. This is repeated until the model judges it has met the goal. This is known as the xref:agent-loop.adoc[*agent loop*].

Two agents powered by the same model but run inside different harnesses will behave very differently, because the harness — not the model — defines the agent's available tools and constraints.

A *session* is one bounded run of interaction with an agent. A session starts empty and incrementally fills the model's *context window* through user messages, tool calls and their results, and the model's own outputs. xref:context-compaction.adoc[*Compaction*] may be used to keep sessions within the model's context window.

Model's are xref:stateless.adoc[*stateless*]. They persist no memory between inference invocations. Everything an agent appears to remember is actually session history re-sent with each new user prompt and tool call response. Harnesses persist sessions to the filesystem as xref:agent-transcript.adoc[*agent transcripts*]. This is what allows past sessions to be resumed and reviewed later.

A *turn* is one user message or tool call response, plus everything the agent does in response, up until it the model yields back to the user or makes another tool. A turn contains one or more xref:inference-provider.adoc[*model provider*] requests. A session consists of one or more turns.

A turn can be a one-sentence answer or twenty minutes of inference. The choice of turn length is the model's.

The gaps between turns are where humans and tools can steer agents. xref:agent-loop.adoc[*Loop engineering*] can be used to control the agent loop in deterministic workflows.

*Human-in-the-loop* is a working pattern where one or more humans pair with an agent during a session, steering the agent at the end of each turn. Human-in-the-loop catches problems while they are cheap. Ambiguous, irreversible, or hard-to-review tasks — a schema migration, a tricky design, anything touching production — suit humans staying in the loop.

This contrasts with xref:away-from-keyboard.adoc[*AFK*], where the agent runs unattended and humans judge the result afterwards.  Well-specified, low-risk, easy-to-verify tasks suit AFK.

== Design concept

The *design concept* is the shared understanding of what is being built, held between user and agent but separate from any asset. Fred Brooks' term (from _The Design of Design_): the conversation, the handoff artifacts, and the code are all assets that try to capture the design concept, but none of them is it. The concept names the gap behind "the agent wrote exactly what I asked for and it's still wrong" — the design concept was not finished in your own head, and the agent filled the silences with its own assumptions.

You can tell the concept is shared when the other party starts answering questions you have not asked, the way you would. Until then the work is conversation, and *grilling* is the deliberate version of that conversation. See xref:agent-handoff.adoc[*agent handoff*].

== Grilling

*Grilling* is a technique for developing a design concept with an agent. The agent interviews the user Socratically, one decision at a time, proposing a recommended answer each time. It slows the rush to a finished plan; no xref:agent-handoff.adoc[*handoff artifact*] is produced until the concept stabilises.

Grilling exists because agents fill gaps silently. Asked to write a spec from a two-line prompt, the agent picks defaults and writes them in, indistinguishable from your own choices. Grilling inverts this: instead of guessing, the agent asks. It is a human-in-the-loop technique — your answers are the input. When a question cannot be answered in conversation, switch to xref:prototyping.adoc[*prototyping*].

== Conductor and orchestrator

As AI takes over more implementation, developers move fluidly between two modes. In *conductor* mode the developer works in real time with an AI pair-programmer – in the IDE, watching code appear, guiding the AI with prompts and corrections, maintaining fine-grained control. The AI is a powerful instrument and the developer is actively directing every movement. This suits complex logic, tricky debugging, and unfamiliar codebases where the developer needs to understand each change as it is made. The risk is that personally directing every keystroke caps the throughput gain.

In *orchestrator* mode the developer operates at a higher level of abstraction – defining goals, assigning them to agents, and reviewing results rather than watching code appear line by line. Agents may work in the background, in parallel, on different parts of a codebase. The developer checks in periodically, reviews output, and gives course corrections. This suits well-defined tasks like bug fixes, features against established patterns, codebase migrations, and test generation, and is the natural mode for xref:away-from-keyboard.adoc[*AFK*] work and xref:agent-orchestration.adoc[*multi-agent delegation*].

The orchestrator demands a different skill set than the conductor: specification (defining tasks precisely enough for unambiguous execution), decomposition (breaking large tasks into appropriately sized units), evaluation (quickly assessing whether output meets the bar), and system design (the constraints, tests, and feedback loops that keep agents productive). The shift is from implementation skill to judgment – directing agents well matters more than writing the most code.

The conductor and orchestrator are two ends of a spectrum, and most real work mixes both. Where the orchestrating role is played by an agent that spawns others, the result is a xref:multi-agent-system.adoc[*multi-agent system*]. The choice connects to xref:agentic-engineering.adoc[*agentic engineering*], xref:loop-engineering.adoc[*loop engineering*], and the human-in-the-loop pattern above.

== Agents versus workflows

At its simplest, an agent is an LLM running in a loop with tools. Given a goal and the context so far, the model decides whether to answer or to call a tool — eg. a search, a database query, an API call, a code execution. It reads the result, adds it to the context, and decides again, repeating until it judges the goal met. This is known as the xref:agent-loop.adoc[*agent loop*].

What separates this from a fixed *workflow* is who controls the flow. In a workflow, deterministic code decides each step. The LLM is a component inside a path that is fixed at design time.

By comparison, in an agent, the model decides the path at runtime — which tool to call next, how many times, and when to stop.

The two are ends of a spectrum, and most production systems sit somewhere along it. The trade-off is predictability against flexibility. A workflow is cheaper, faster, easier to test, and fails in ways you can anticipate. It suits tasks whose steps are known in advance. An agent copes with open-ended tasks where the steps cannot be enumerated beforehand, at the cost of higher latency and spend, variable run lengths, and failures that are harder to predict.

A good default is to design an agentic system to have the least autonomy that solves the problem. For example, start with a single model call, then to move to a longer workflow when the steps are known, and reach for an agent only where the model genuinely needs to decide the steps. A common hybrid embeds an agent as one step inside an otherwise fixed workflow.

(See also xref:workflow-management-system.adoc[*workflow management systems*].)

== Agent development frameworks

Designing and operating an agent harness is a discipline in its own right — known as xref:agent-harness.adoc[*harness engineering*].

An *agent framework* or *SDK* is a library for building custom agents, providing the infrastructure for building and orchestrating them. It's important to distinguish between two types:

* *Development frameworks*: Code libraries and SDKs used to write agent code. These are tools for building agents.

* *Agent harnesses*: Runtime environments and orchestration systems that execute agents, manage their lifecycle, control permissions, provide observability, and coordinate multi-agent workflows. Some of these blur the line by offering both development and runtime capabilities.

Many frameworks require a harness to run agents in production, while some frameworks include built-in harness capabilities. The distinction helps clarify whether you're looking for a tool to _write_ agent code or an environment to _run_ agents.

Frameworks differ mainly in how much control they give you over the flow. Some supply components and prebuilt agent constructors for a quick start. Others model an agent as an explicit graph of nodes with persisted state, which gives control over branching, human-in-the-loop approval, and long-running runs. Vendor SDKs ship the vendor's own agent loop with built-in tools. Almost all lean on typed schemas to validate model output, which is also how tool calling works, since LLM output is unreliable text. When validation fails, the error can be fed back to the model so that it corrects itself.

The frameworks, SDKs, and platforms that I've collected, grouped by purpose, are in my bookmarks: see xref:bookmarks::applications/ai/agent-frameworks/index.adoc[*AI agent frameworks and SDKs*]. They include general-purpose frameworks, multi-agent frameworks and orchestration platforms, data and RAG frameworks (see xref:retrieval-augmented-generation.adoc[*retrieval-augmented generation*]), vendor SDKs, and self-hosted harnesses. Agent products are listed under xref:bookmarks::applications/ai/agents/index.adoc[*AI agents*], and agent benchmarks such as Terminal-Bench under xref:bookmarks::applications/ai/benchmarks/index.adoc[*benchmarks and leaderboards*].

== Anatomy of an agent

Building an agent means assembling six pieces. Frameworks and xref:agent-harness.adoc[*harnesses*] package them in different ways, but all six are present in any working agent, whether supplied or neglected.

* *Model.* The reasoning engine. Its capability sets the ceiling on how well the agent can plan, choose tools, and recover from errors, while its price and latency set the cost of every iteration of the loop. Agents often mix models, using a stronger one to plan and a cheaper one for routine steps.

* *Tools.* Functions the model can call, each described to the model by a name, a natural-language description, and a typed parameter schema, commonly expressed as xref:json-schema.adoc[*JSON Schema*]. The xref:model-context-protocol.adoc[*Model Context Protocol*] standardizes how tools are exposed to agents.

* *Instructions.* The system prompt and the policies that sit alongside it: the agent's role, the goal, the constraints, and what to do when stuck. See xref:prompt.adoc[*prompt*].

* *Memory and state.* The conversation so far, which is the agent's working memory and is bounded by the xref:context-window.adoc[*context window*], plus any longer-term store that outlives a session. See xref:agent-memory.adoc[*agent memory*].

* *Orchestration.* The loop itself, with the logic around it: xref:retry.adoc[*retries*] for transient failures, validation of tool calls, xref:guardrail.adoc[*guardrails*] on what the agent may do, and stopping conditions such as a step limit or budget cap that prevent a xref:runaway-loop.adoc[*runaway loop*]. Where several agents cooperate, this extends to xref:agent-orchestration.adoc[*agent orchestration*].

* *Observability and evals.* The means of seeing what the agent did and judging whether it did it well: xref:tracing.adoc[*tracing*] and xref:ai-eval.adoc[*evals*].

Of the six, the model is the only one an agent developer usually does not build. The rest are the harness. See xref:agent-harness.adoc[*agent harness*] for how they fit together in practice.
