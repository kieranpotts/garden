= Software architecture

*Software architecture* has many definitions, but they can all be reduced to just two primary meanings.

* Software architecture is the process of designing software.
* Software architecture is the description of the high-level structure of a software system.

Most commonly, software architecture is understood to refer to a series of *architectural views* that are used to
*document* how a system is decomposed into *components*, *cross-cutting concerns*, and *interfaces* (both internal and
external).

Software architecture also describes the xref:architectural-pattern.adoc[*architectural patterns*] and styles that
govern how those *building blocks* are composed. A xref:layered-architecture.adoc[*layered architecture*], a
xref:client-server-architecture.adoc[*client-server architecture*], and a xref:microservices.adoc[*microservices*]
system are all descriptions of structure.

== Software architecture versus software design

The terms "*software architecture*" and "xref:software-design.adoc[*software design*]" are used interchangeably, and
they mean different things at different scales, across different domains, and in different organizations. Nevertheless,
drawing a general-purpose distinction between the two concepts is useful.

It is commonly understood that software architecture operates at a higher level of abstraction than software design.
Whereas design is concerned with *low-level design*, code constructs — individual modules, classes, and functions — and
the xref:design-pattern.adoc[*design patterns*] that shape them, architecture deals with the *high-level design* of a
system as a whole — its major components, the responsibilities assigned to each, and the relationships and interfaces
between them.

The xref:high-level-design.adoc[*high-level design*] captures the architectural views, while the *low-level design*
fills in the implementation detail of individual components.

But the boundary is not sharp, and what counts as an architectural decision in one system is a routine design choice in
another.

A better definition — one that is more universally applicable — is that software architecture is about design decisions
that have system-wide effects, shaping many components, that are hard or expensive to change later, or that have other
significant consequences.

Choosing a xref:monolith.adoc[*monolith*] over a distributed deployment, deciding how data is partitioned, or settling
on a particular xref:event-driven-architecture.adoc[*event-driven*] style are architectural decisions because they
constrain almost all other design decisions that follow. By contrast, selecting a design pattern for the internal
structure of a single class is a local decision that is easily reversible.

Some design decisions may be highly localized in the code and configuration they touch, yet have far reaching
consequences. Changing a database's default transaction isolation level, adjusting a load balancer's health-check
timeout, or flipping a shared feature flag's default value are each a one-line change but have potentially big blast
radiuses. By our improved definition, these are architectural design decisions, though the implementation is highly
localized.

A design decision could also be considered to be architectural in nature when it resolves a significant business
xref:requirement.adoc[*requirement*] or technical constraint, it is driven by xref:quality-attribute.adoc[*quality concerns*]
more than functional behavior, or it trades one quality against another.

Ultimately, the distinction between software architecture and software design is a matter of judgment, and that judgment
shifts with the scale and domain of the system under development.

== Other architectural domains

Software architecture is scoped to a single software system. The word "architecture" is also used for structure at
wider scopes, or in different media.

xref:enterprise-architecture.adoc[*Enterprise architecture*] operates at the scale of a whole organization. It is
concerned with the entire landscape of applications, data, and infrastructure, and how that landscape serves the
organization's strategy and xref:business-architecture.adoc[*business architecture*] — which systems should exist, which
should be retired, and how they fit together.

*Solution architecture* sits between the two, shaping how several systems, often a mix of bought and built, combine to
solve a particular business problem within the constraints set by the enterprise architecture.

*Technical architecture*, also called *infrastructure architecture* or *technology architecture*, describes the
platforms that software runs on — hardware, networks, cloud services, operating systems, and middleware.

*Information architecture* describes how data is structured and flows across systems. In user experience design the
same term refers to how content is organized for its users.

*System architecture* is the most ambiguous term of all, its meaning depending on whether "system" refers to a piece of
software, a combination of hardware and software, or a whole socio-technical system.

These domains overlap, and in a small organization one person may cover all of them. The distinction is chiefly one of
scope. Software architecture looks inside one system, while the other domains look across many systems, or beneath
them to the infrastructure they depend on.

== Why software architecture is important

Software architecture is important because the xref:quality-attribute.adoc[*quality attributes*] of a software system
are determined largely by the system's architecture.

Quality is the outcome of both the _process_ that was used to design the software, and the software's resulting
_structure_.

Software qualities, captured as xref:non-functional-requirements.adoc[*non-functional requirements*], include
xref:availability.adoc[*availability*], xref:performance.adoc[*performance*], xref:scalability.adoc[*scalability*],
xref:security.adoc[*security*], xref:modifiability.adoc[*modifiability*], and xref:testability.adoc[*testability*].
Such qualities are in
frequent tension with one another, and reconciling them is the central work of the software architect.

Software architecture serves as a bridge between xref:requirement.adoc[*requirements*] and *implementation*. It
translates what a system must do into the structures that will do it. As a process, software architecture is the
earliest point at which the consequences of new requirements can be reasoned about and assessed for their feasibility
and risks.

Software architecture is the primary medium through which technical and non-technical stakeholders in a software project
communicate with one another. Different audiences need different *architectural views*. *Developers* need module
structure, *operators* need deployment topology, and *sponsors* need to see how the design meets business goals.

The practice of xref:architectural-knowledge-management.adoc[*recording architectural*] decisions, views, and
xref:design-rationale.adoc[*rationale*], in artifacts such as xref:c4-model.adoc[*C4 models*] and
*architecture decision records*, greatly aids communication within technical teams and between technical teams and
business stakeholders.

== The elements of software architecture descriptions

Most architectural descriptions are built from a small set of recurring elements.

* *Components* are the _processing elements_ that do the work, eg. modules, services, layers, processes, or subsystems.
  Each carries a coherent responsibility.

* *Data* is the information structures that flow through the system and are operated on by the components.

* *Connectors* are the mechanisms by which components interact, eg. procedure calls, event buses, message queues, shared
  databases, or network protocols.

* *Configurations* are the topological arrangements of components and connectors, eg. layered, pipe-and-filter,
  brokered, or event-driven.

* *Properties* are the qualities the structure is intended to deliver, eg. low xref:coupling.adoc[*coupling*], high
  xref:cohesion.adoc[*cohesion*], and *conceptual integrity*.

The design of these elements is guided by xref:design-principle.adoc[*design principles*] such as the
*separation of concerns*, xref:abstraction.adoc[*abstraction*], and xref:encapsulation.adoc[*encapsulation*].

Besides the code, configuration, and data schema of the software system, other artifacts capture architectural
decisions, their rationales, trade-offs considered, and assumptions made. Such artifacts help to keep a software
architecture coherent as a system *expands* over time. They also help to transfer valuable knowledge to future
maintainers.

== Architectural drivers and constraints

Software architecture is primarily driven by a system's non-functional requirements, which determine the quality
attributes the system must exhibit.

Architecture is also constrained by the structure of the organization that builds it — see *Conway's law* — and by the
existence of legacy systems and the technical debt they carry. Available technology and the skills and experience of
the delivery teams also determine what architectures can be developed, maintained, operated, and sustained.

Much of software architecture involves making *trade-offs* between competing quality attributes. Hardening security
usually costs performance. Maximizing availability adds redundancy that hurts conceptual integrity. Strong consistency
works against latency.

Monolithic versus distributed, synchronous versus asynchronous, and SQL versus NoSQL, are just a few examples of classic
trade-off pairs that recur across system designs.

.The first law of software architecture
[quote, Mark Richards and Neal Ford, Fundamentals of Software Architecture (O'Reilly)]
____
Everything in software architecture is a trade-off.
____

== Up-front versus evolutionary architecture

How much of an architecture is fixed up front, and how much is allowed to emerge, depends on the cost of change and the
stability of the requirements.

xref:big-design-up-front.adoc[*Big design up-front*] suits environments where change is expensive and requirements are
stable. xref:evolvability.adoc[*Evolutionary architecture*] — which means to build the capacity for change into the
software design itself — suits business *domains* where there are high levels of uncertainty.

In reality, most systems blend the two approaches. An initial architecture is designed to satisfy the non-functional
requirements, and is subsequently *iterated* on through a process of stepwise refinement as more is learnt about the
software's domain and the requirements on it.

Evolutionary design is best avoided at the highest abstractions of a system, in which the broad *architectural styles*
and *communication patterns* of the system are established, due to the xref:project-paradox.adoc[*project paradox*].

// == Definitions of software architecture

// Formal standards have tried to pin the definition down further than the two-meanings summary above. The IEEE 1471
// standard defined software architecture as *the fundamental organization of a system embodied in its components, their
// relationships to each other and to the environment, and the principles guiding its design and evolution*. The successor
// standard, ISO/IEC/IEEE 42010:2011, generalized this beyond software to any system: *fundamental concepts or properties
// of a system in its environment embodied in its elements, relationships, and in the principles of its design and
// evolution*.

// Both definitions turn on the same four ideas.

// * *Components* (or elements) are the structural building blocks of a system — subsystems, modules, classes, functions —
//   usually realized in a programming language, though other artifacts can play the role too.
// * *Relationships* are the interfaces, dependencies, and associations through which components interact, enabling
//   xref:separation-of-concerns.adoc[*separation of concerns*].
// * *Environment* is everything a system exchanges data, control flow, or events with, without itself containing.
// * *Principles* are the rules and conventions — often called concepts or solution patterns — that hold across a system
//   or large parts of it, and that give it xref:conceptual-integrity.adoc[*conceptual integrity*].

// The Software Engineering Institute maintains a running collection of further definitions, itself a symptom of how
// unsettled the term remains. And although "software architecture" usually names the structure of one IT system, the same
// term is also used for architecture as an engineering discipline in its own right — the body of methods, notations, and
// practice, rather than any single system's structure.

// == Tasks and responsibilities of software architects

// Software architects are responsible for meeting a system's requirements and shaping its architecture design,
// aligning that responsibility with the overall project responsibility held by project management or other roles,
// depending on the process model in use. Their core tasks are to:

// * clarify and scrutinize requirements and constraints, agreeing any necessary refinements with the relevant
//   stakeholders;
// * decide how to decompose the system into building blocks, and determine the dependencies and interfaces between
//   them;
// * decide on cross-cutting concerns such as persistence, communication, and the user interface;
// * communicate and document the architecture through views, architectural patterns, and cross-cutting and technical
//   concerns;
// * accompany the system's realization and implementation, folding stakeholder feedback back into the architecture and
//   checking that the source code stays consistent with it;
// * analyze and evaluate the architecture, especially the risks it carries against meeting the requirements; and
// * identify, highlight, and justify the consequences of architectural decisions to other stakeholders.

// Underlying all of these is the need to recognize where iteration is necessary, and to seek out the feedback that makes
// each iteration count.

// An architect adapts how they communicate to whichever stakeholders they are addressing: product management and
// product owners, project managers, requirements engineers (business or requirements analysts, requirements managers,
// system analysts, business owners, subject-matter experts), developers, quality assurance and testers, IT operators
// and administrators, hardware developers and system architects on embedded or hardware-related systems, and
// enterprise architects and architecture-board members. Recognizing each stakeholder's concerns, and how those concerns
// bear on the architecture or on the development process itself, is part of the job, as is spotting the conflicts that
// surface between short-term goals — business and project pressure — and long-term ones — architecture and
// maintainability. Resolving such conflicts means bringing the affected stakeholders into the conversation, often
// through structured techniques such as stakeholder interviews, which also surface requirements that are missing or
// that conflict with each other.

// Both requirements and constraints shape the architecture and the process of arriving at it, and an architect's own
// decisions can in turn create new requirements or force existing ones to change. The constraints worth tracking fall
// into a few recurring categories.

// * *Product-related requirements* – functional requirements and quality requirements.
// * *Technological constraints* – existing or planned hardware and software infrastructure, constraints on data
//   structures and interfaces, reference architectures, libraries and frameworks, and the programming languages
//   available.
// * *Organizational constraints* – the structure of the development teams and the customer's organization
//   (particularly xref:conways-law.adoc[*Conway's law*]), company and team culture, partnerships and cooperation
//   agreements, standards and process models, and the budget, time, staff, and skills available.
// * *Regulatory constraints* – local and international law, contract and liability issues, data protection and
//   privacy, and compliance obligations.
// * *Trends* – market trends, technology trends such as cloud, microservices, containers, and generative AI, and
//   methodology trends such as Agile.

// Making the assumptions behind a design explicit is as important as tracking these constraints formally: unstated
// assumptions are a common source of misunderstanding between stakeholders who each assumed something different.

// Beyond gathering and reconciling these inputs, an architect is expected to design and document architectures against
// known functional and quality requirements — for the ordinary run of systems that are neither safety- nor
// business-critical — and to make the structural decisions this requires: how the system decomposes into building
// blocks, what dependencies exist between them, and which trade-offs and interdependencies between architecture
// decisions need to be recognized and justified. This includes thinking in terms of xref:black-box-view.adoc[*black-box*]
// and xref:white-box.adoc[*white-box*] views of a component, applying xref:stepwise-refinement.adoc[*stepwise
// refinement*] to work from a coarse structure down to detail, and designing the xref:architecture-view.adoc[*architecture
// views*] — particularly the building-block, runtime, and deployment views — that communicate the result. It also means
// explaining the consequences of a decision on the source code that implements it, separating and justifying the
// technical and domain-related elements of the architecture, and identifying the risks each decision carries.

// == Goals and benefits of software architecture

// These tasks serve a small set of concrete goals: software architecture supports the design, implementation,
// maintenance, and operation of a system; it achieves the system's functional requirements, and non-functional ones such

// concepts understood by everyone with a stake in it; it reduces complexity systematically rather than leaving that to
// chance; and it yields concrete, architecturally relevant guidelines for implementation and operation to follow.
