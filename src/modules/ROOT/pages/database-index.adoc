= Database index

// 📝 DRAFT

:link-algomaster-indexes: https://blog.algomaster.io/p/a-detailed-guide-on-database-indexes
:link-progress-indexes:   https://www.progress.com/tutorials/odbc/using-indexes

image::database-indexes.svg[opts=inline]

A database index is an auxiliary data structure that lets a database engine find rows without scanning the whole table. It holds the indexed column values in sorted order, each paired with a pointer back to the row it came from. The analogy is a book's index. Instead of flipping through every page to find a term, you look the term up in a sorted list and jump straight to the cited page.

Without an index, the database must perform a *full table scan*, reading and testing every row against the query condition. On a large table that is prohibitively slow. With an index, the engine follows the pointers in the index to fetch only the matching rows. What would be an O(n) scan becomes an O(log n) lookup, an improvement xref:big-o-notation.adoc[*big O notation*] captures precisely.

Indexes are built on standard xref:data-structure.adoc[*data structures*]. The default in most relational engines is a *B-tree* or its variant the *B+ tree*, which stays balanced as rows are inserted and deleted, keeps values sorted for range queries, and packs each node to match a disk block so few disk reads are needed. *Hash indexes* use a hash function to map keys to buckets, giving O(1) equality lookups but no support for ranges or ordering. *Bitmap indexes* use one bit per row per distinct value, and suit low-cardinality columns in analytical workloads.

== Trade-offs

Indexes speed up reads but slow down writes. Every insert, update, or delete must update the index as well as the table, so each extra index adds work to the write path. Indexes also consume disk space, sometimes more than the table itself. The right balance depends on the system's xref:access-pattern.adoc[*access patterns*]. Indexes pay off most for read-heavy workloads, while write-heavy systems may be better served by fewer indexes.

Indexes also get harder in a xref:sharding.adoc[*sharded*] database. An index on the shard key stays local to each shard, but a secondary index on any other column either has to be partitioned per shard, forcing every lookup to fan out across the cluster, or maintained as a separate global structure, which adds a second distribution dimension on top of the data itself.

== Choosing what to index

An index is only useful if a query can use it. A few rules of thumb:

* Index columns that appear frequently in `WHERE`, `JOIN`, and `ORDER BY` clauses.
* Prefer high-cardinality columns. An index on a unique `customer_id` is far more selective than one on a `gender` column with three values.
* Match the index to the query exactly. Wrapping an indexed column in a function, eg. `WHERE UPPER(last_name) = 'SMITH'`, prevents an index on `last_name` from being used. A function-based index on `UPPER(last_name)` is needed instead.
* In a composite index, order columns from most to least selective. The index serves queries that filter on its leading column or columns, but not those that skip it.

== Common types of indexes

* *Primary key index.* Created automatically for the primary key, enforcing uniqueness and giving fast lookups by that key.
* *Clustered index.* Determines the physical storage order of the table's rows. Only one clustered index can exist per table, so the table and the index are effectively the same structure.
* *Secondary index.* Any index on a non-primary-key column, eg. an index on `email` to speed up login lookups.
* *Composite index.* An index on multiple columns, useful for queries that filter on those columns together, eg. finding a user by first and last name.
* *Covering index.* An index that includes every column a query needs, so the engine can answer the query from the index alone without touching the table.

The types overlap. Whether an index is primary, secondary, or covering describes its relationship to the table and the query, not its structure. A secondary index entry holds either a pointer to the row's physical location or, in engines where the table is clustered on the primary key, the primary key value. Either way, a lookup through a non-covering secondary index costs a second step to fetch the row. A covering index avoids that step, and many engines let an index carry extra non-key *included columns* for this purpose. These are stored in the index's leaf entries so they can satisfy a query's `SELECT` list, but they are not sorted or searchable, so they add less maintenance cost than making them part of the key.

== B-trees and LSM-trees

Two storage-engine designs dominate how indexes are maintained on disk, and they make opposite trade-offs between reads and writes.

A *B-tree* updates pages in place. A write finds the right page and modifies it, usually after appending to a write-ahead log for crash safety. Reads are predictable, since a lookup touches a small, fixed number of pages. Writes are more expensive, because a small change rewrites a whole page, and random writes cause random disk I/O. B-trees are the default in most relational databases.

A *log-structured merge-tree (LSM-tree)* never updates in place. Writes go to an in-memory sorted buffer, which is flushed to disk as an immutable sorted file when full. A background process merges these files, a step called *compaction*, to keep their number down and discard overwritten and deleted entries. Writes are sequential and fast, and the immutable files xref:data-compression.adoc[*compress*] well. Reads may have to check several files, which is why LSM engines use a xref:bloom-filter.adoc[*Bloom filter*] per file to skip those that cannot contain a key. Compaction competes with foreground traffic for I/O, and rewriting data during compaction causes *write amplification*. LSM-trees are common in xref:wide-column-store.adoc[*wide-column stores*], xref:key-value-store.adoc[*key-value stores*], and other write-heavy systems.

As a rule of thumb, B-trees favor read-heavy workloads with predictable latency, and LSM-trees favor write-heavy workloads and high ingest rates.
