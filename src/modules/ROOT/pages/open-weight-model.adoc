*Open-weight* models are xref:large-language-model.adoc[*large language models*] (or other machine learning models) whose trained weights are published for anyone to download and run. This is distinct from *open-source*, which would also require the training data and code used to produce the model to be public.

== Open weight vs. open source

Most "open" AI models are only open-weight. The weights are downloadable, but the training corpus, the data-cleaning recipes, and the exact training code are kept private. That is enough for many use cases — you can run, fine-tune, and self-host the model — but it is not enough to reproduce it from scratch, audit what it was trained on, or verify that a given output is free of inherited copyright or bias issues.

A smaller but growing category is *truly open-source* models, which release the weights _and_ the training data and methodology. The standout example is Nvidia's {link-nemotron-3}[*Nemotron 3*] family, announced alongside a partnership with Palantir in July 2026. Nvidia published not just the model weights but the training recipes and roughly ten trillion tokens of the underlying training data. That level of openness makes it possible to inspect, reproduce, and modify the full pipeline, not just the final artifact.

The distinction matters for several reasons:

* *Reproducibility and auditability.* Open-source models let researchers and regulators inspect what went into the model. Open-weight models do not.

* *Data sovereignty and IP risk.* Running an open-weight or open-source model on your own hardware keeps proprietary prompts and data inside your infrastructure. More fully open models also make it easier to avoid the training-data copyright questions that have led to large settlements against closed labs.

* *Cost.* When performance is roughly equivalent, self-hosting an open model is often an order of magnitude cheaper per token than using a closed frontier API.

Licensing terms vary between open-weight models. Some permit unrestricted commercial use (eg. Apache 2.0, MIT). Others carry custom licenses that restrict commercial use, redistribution, or use above a certain scale (eg. Meta's Llama community license).

{link-huggingface}[Hugging Face] is the primary hub for discovering and downloading open-weight models, hosting over two million models contributed by individuals, research labs, and major organizations. The other major resource in this space is {link-ollama-search}[Ollama's model database], which is a more curated library of models that are proven to be stable with the Ollama model manager (see xref:model-access-layer.adoc[*model access layer*]).

There are pros and cons to running open-weight models on your own hardware:

* Free (just the cost of the hardware and electricity).
* Highly customizable.
* Secure and private.
* Zero network latency.
* Work offline (no internet connection required).
* High availability. Can be run 24/7/365.
* Six to 12 months behind the frontier models in capability.
* Require a lot of RAM and GPU VRAM to run large models.

== Hardware requirements

It is useful to think of open-weight models as falling into a spectrum of size tiers, with each tier having different minimal hardware requirements:

* *Ultra-light (1–3B)*: Run on almost any machine with 8 GB+ RAM. Capable of basic chat and simple tasks.

* *Small (3–8B)*: A good balance of quality and speed. Need ~8–16 GB RAM. The recommended starting point for most local setups.

* *Medium (8–13B)*: Well-rounded general-purpose models. Run well on 16–24 GB RAM with a mid-range GPU.

* *Large (30–70B)*: High capability. Require at least 32 GB RAM and a dedicated GPU with 24+ GB VRAM.

* *Very large (70B+)*: Near-frontier capability. Require high-end workstations with multi-GPU setups and at least 64 GB each of RAM and VRAM.

=== Memory for the weights

Memory capacity is the hard limit. The model's weights must fit in memory (VRAM, or system RAM for CPU inference) before anything else matters, and a model that does not fit will not load. The weights are not the whole footprint. As a rule of thumb, add 2–4 GB to the weight size for a comfortable total, and a further 4–8 GB for contexts of 16K tokens or more. The extra goes mostly on the KV cache, which takes roughly 0.5–2 GB at a 4K context and 2–8 GB at 32K. Leave another 2–4 GB for the operating system.

=== Speed and memory bandwidth

Capacity decides whether a model runs. *Memory bandwidth* decides how fast. Generating each token means reading through the model's active weights, so token generation speed scales with how quickly memory can be read. GPUs have roughly 5–20 times the memory bandwidth of system RAM, which is the main reason they are so much faster than CPUs for inference. Raw compute matters most for prompt processing and the time to the first token.

Some approximate figures, for a 7B model at Q4:

* *CPU only*: about 8–20 tokens per second, depending on the CPU and RAM speed. This is viable for small models and light use, as 10–15 tokens per second is already faster than reading speed. Faster RAM helps directly: DDR5 gives roughly 30–50% faster CPU inference than DDR4.

* *Mid-range GPU* (eg an RTX 3060 with 12 GB): about 40–55 tokens per second.

* *High-end GPU* (eg an RTX 4090 with 24 GB): about 90–120 tokens per second.

Storage affects only how long a model takes to load, not how fast it generates. An NVMe SSD loads a model in about 2–10 seconds, against 30 seconds to two minutes or more from a hard disk. Model files range from about 2 GB to over 50 GB each, so a collection that includes 30–70B models needs 200–500 GB.

=== Choosing hardware

Existing hardware is enough to start. A machine with 16 GB of RAM can run 7–8B models on the CPU, as can a GPU with 6 GB or more of VRAM. Beyond that, there are three main routes:

* *A single Nvidia GPU.* This gives the most speed for models that fit in its VRAM, and the best software support, including CUDA-only tools and fine-tuning. Consumer cards top out at 24 GB, which runs models up to about 30B at Q4. A used RTX 3090 (24 GB) is often recommended as the best value.

* *Apple Silicon.* The CPU and GPU share one pool of *unified memory*, so a Mac with 64 GB or more can run models far too large for any single consumer GPU, quietly and at a fraction of the power draw (30–80 W under load, against 400–600 W for a desktop with a high-end GPU). The trade-offs are lower speed for models that would fit on a GPU, and weaker support for fine-tuning and CUDA-based tooling.

* *Multiple GPUs.* VRAM is pooled by splitting the model's layers across cards, which works with mixed GPUs but runs at only about 50–70% of single-GPU efficiency. Two 24 GB cards give 48 GB, enough for a 70B model at Q4. Power draw and noise rise accordingly.

When upgrading an existing machine, the priorities in order of impact are: add a discrete GPU (typically 3–8 times faster than CPU only), then more VRAM, then more system RAM, then faster RAM, then an NVMe SSD.

=== System RAM for loading a model

VRAM is not the only constraint. Even when all GPU memory is dedicated to inference and the quantized model fits in it, the machine needs enough system RAM to load the model in the first place. These are approximate figures for models quantized to about 4 bits (eg Q4_K_M):

[cols="1,1,3"]
|===
|Model size (parameters) |Approx. weight size |Typical system RAM needed for loading

|7–8B
|~5 GB
|*12–16 GB*. Enough for the checkpoint, staging buffers, and a modest context window.

|13–14B
|~9 GB
|*24 GB*. Covers the larger weight file and extra KV cache space for typical prompts.

|30–32B
|~20 GB
|*48 GB*. Needed to load the model and keep the KV cache for normal context lengths.

|70–72B
|~42 GB
|*64 GB+*. The model plus context storage, especially with context windows beyond 4K tokens.

|120B (eg `gpt-oss-120b`)
|~63 GB
|*64 GB* minimum. Any extra RAM helps with larger contexts or concurrent applications.
|===

[NOTE]
====
The weight sizes are close to real file sizes. The RAM figures are conservative planning estimates, not measured minimums. Runtimes such as llama.cpp memory-map the model file, so with the model fully offloaded to the GPU, actual system RAM use is often well below the size of the weights.
====

System RAM matters even when VRAM does the inference because:

* The model file is read from disk and passes through system memory on its way to the GPU.

* The runtime may create intermediate staging buffers during the transfer, for example to convert the weight layout, which add to the memory needed at load time.

* The KV cache (the attention state kept for each token of context) can spill into system RAM when VRAM runs short, and it grows with context length.

* The operating system and other processes need headroom, or they will trigger out-of-memory crashes.

As a rule of thumb:

* *Small models (up to 8B)*: 16 GB of RAM is comfortable.

* *Mid-size models (around 14B)*: 24–32 GB.

* *Large models (30–70B)*: 48 GB is the safe minimum, or 64 GB for 70B and up.

* *Very large models (100B+)*: 64 GB or more, and preferably 128 GB for long contexts or running multiple models.

With much less RAM than this, loading can fail with out-of-memory errors, or slow to a crawl through swapping, even if the GPU has enough VRAM for the quantized model. Adding RAM is the most straightforward way to widen the range of models you can run locally.

Custom hardware like the {link-dgx-spark}[Nvidia DGX Spark] give you the ability to run _and train_ large language models on your own hardware.

== Open-weight model families

As of 2026, some notable open-weight model families include (several use a xref:large-language-model.adoc#_mixture_of_experts[*mixture-of-experts (MoE)*] architecture):

* {link-llama}[*Llama*] models from Meta. The Llama family did much to kick-start the open-weight era, and its widespread adoption has made the underlying architecture a de facto reference point that many other open models build on. The Scout variant is known for its massive 10-million token context window. Released under Meta's community license, which permits commercial use but imposes some restrictions (including for very large deployments).

* {link-gemma}[*Gemma*] models from Google. These are Google's open-weight counterparts to its proprietary, frontier Gemini models. Gemma models are optimized to run on consumer hardware.

* {link-qwen}[*Qwen*] models from Alibaba Cloud are available in a wide range of sizes, so there'll always be one variant that you can run on your hardware.

* {link-mistral}[*Mistral*] models from Mistral AI, a French company that produces both open-weight models and proprietary models accessible via web service APIs. Their Mixtral models helped popularize the mixture-of-experts (MoE) architecture in open models.

* {link-phi}[*Phi*] models from Microsoft. A family of small language models (SLMs) that punch well above their size on reasoning and maths, achieved largely by training on high-quality, "textbook-quality" filtered and synthetic data rather than sheer scale. Optimized for on-device and edge use, and released under the permissive MIT license. Recent releases include Phi-4 (14B) and the compact Phi-4-mini, with multimodal variants.

* {link-gpt-oss}[*gpt-oss*] models from OpenAI. `gpt-oss-120b` and `gpt-oss-20b`, released under the permissive Apache 2.0 license in August 2025, were OpenAI's first open-weight models since GPT-2.

* {link-kimi}[*Kimi*] models from Moonshot AI. Kimi K2.5 (released January 2026) is an open-weight mixture-of-experts model with 1T total parameters (32B xref:large-language-model.adoc#_active_parameters[*activated*] per token) and a 256K-token context window. It matches frontier models on several benchmarks and is multimodal across text, code, image, and video (understanding only, no generation). Kimi 2.5 leads in mathematical reasoning and is optimized for "agent swarming".

* {link-glm}[*GLM*] models from Z.ai (formerly Zhipu AI). The GLM-4.5 and GLM-4.6 releases are strong open-weight MoE models, well-regarded for their "interleaved thinking" and demonstrated capabilities in both agentic and vibe coding workflows.

* {link-deepseek}[*DeepSeek*] models from DeepSeek AI. This AI lab made waves in early 2025 when DeepSeek-R1 demonstrated near-frontier reasoning performance at a fraction of the training compute cost that had previously been assumed was necessary to develop frontier models. Its "engram" memory system has been proven to maintain high coding performance across 1M+ token contexts.

* {link-minimax}[*MiniMax*] models from MiniMax AI, which also develops closed-weight models. MiniMax M2.5 is well-regarded, posting near-frontier agentic and coding scores (~80% on SWE-Bench Verified) at an exceptionally low cost.

Nvidia continues to expand its open-weight offerings, most recently with the {link-nemotron-3}[*Nemotron 3*] family (Nano, Super, and Ultra variants).

== Open-weight coding models

The following open-weight models are highly regarded for programming tasks. Small models (≤ 8B) run comfortably on a laptop or CPU-only setup. Larger models require a GPU with ≥ 16–24 GB VRAM.

Not all of them support *tool calling* (also called function calling) — the ability to emit structured calls to external tools/functions as part of a response. This is a prerequisite for agentic coding workflows, where the model must be able to invoke tools such as file edits, shell commands, or search. Models without native tool-calling support can still be used for plain code generation, completion, or chat, but are not suitable as the driver of an agent loop without a third-party fine-tune or adapter bolted on.

* *Qwen3.8-27B*: Alibaba's flagship model in the 27B class, released August \2026. A dense, natively multimodal model (text, image, and video input) built for agentic, long-horizon coding tasks, with flexible thinking control and a 262K native context window (extensible to 1M via YaRN). Available on all Ollama-supported platforms. Apache 2.0 license. + *Tool calling: supported natively.* Uses a `<tool_call>` XML format; Qwen-Agent is the recommended harness for making full use of its agentic tool-calling ability.

* *Nvidia Nemotron 3.5 Lightning*: A hybrid Mixture-of-Experts model (30B total, 3B active) from Nvidia, released August 2026, purpose-built for the execution layer of always-on agents — reading files, calling tools, sorting results, and retrying failures. Designed to run on local hardware (RTX PCs, RTX PRO workstations, DGX Spark/Station) rather than the datacenter, keeping agent context on-device. 1M token context. Uses speculative decoding (multi-token prediction, DFlash/DSpark) for up to 4x the throughput of comparable open models. Open weights and open training data. Apache 2.0 license. + *Tool calling: supported natively.* Trained specifically for tool calling, instruction following, and multi-turn agentic work, for use in harnesses such as Claude Code, Hermes Agent, and OpenClaw.

* *Muse Glimmer*: A 30B multimodal model from Meta Superintelligence Labs, released August 2026 — Meta's first model under that new lab and a notable departure from the Llama family's community license. Built for agent workloads that run locally, with 128K+ context and controllable reasoning strength (low/medium/high/xhigh — use high or xhigh for complex coding and agentic tasks). Available via Ollama's MLX engine on Apple Silicon, with broader platform support following. Apache 2.0 license. + *Tool calling: supported natively.* Reliable schema-based tool invocation across extended, multi-turn workflows, including diagnosing and retrying failed or unexpected tool results.

* *Qwen2.5-Coder 32B Instruct*: Alibaba's dedicated coding model that consistently tops open-weight coding benchmarks. Strong across Python, JavaScript, Go, and SQL. Supports a 32K context window. Apache 2.0 license. +
  *Tool calling: supported natively.* Trained for multi-turn tool/function calling using a Hermes-style `<tool_call>` format, recognized out of the box by inference servers such as vLLM.

* *DeepSeek-Coder-V2 Instruct*: A Mixture-of-Experts model (236B total, 21B active) with very strong multi-language coding performance and a 128K context window. One of the most capable open-weight options for complex, multi-file tasks. MIT license. + *Tool calling: not supported.* The official instruct release has no native function-calling format. Community fine-tunes exist that bolt it on, but it's not built in.

* *Codestral 22B*: Mistral AI's dedicated code model, optimized for low-latency code completion and fill-in-the-middle (FIM) tasks. Well suited to IDE integration. Supports 32K context. Mistral AI Non-Production License (commercial use requires a separate agreement). + *Tool calling: not supported.* A deliberate design choice by Mistral — Codestral targets completion/FIM, not agentic use. Other Mistral chat models (eg. Mistral Large) do support tool calling.

* *StarCoder2 15B*: The successor to StarCoder, trained on The Stack v2. Strong on Python, JavaScript, and C/C++, and well suited to code search and autocompletion tasks. Apache 2.0 license. + *Tool calling: not supported.* The base model is only lightly instruction-tuned and has no function-calling format.

* *Code Llama 70B Instruct*: Meta's instruction-tuned coding variant of Llama 2, with a 16K context window and strong performance on multi-language tasks and large-scale refactoring. Meta's non-commercial license restricts use to research. + *Tool calling: not supported.* No native tool-calling format from Meta for this release. Later, non-coding Llama 3.x Instruct models are the better choice if tool calling is required from the Llama family.
