= Retrieval-augmented generation (RAG)

// 📝 DRAFT

:link-perplexity: https://www.perplexity.ai/

*Retrieval-augmented generation (RAG)* is a technique that combines a xref:large-language-model.adoc[*large language model*] with an external knowledge source, which is retrieved at xref:inference.adoc[*inference*] time and loaded into the model's xref:context-window.adoc[*context window*].

RAG addresses two core limitations of LLMs. The first is that a model's knowledge is frozen at the point of training. By default, models cannot access new information or browse the web. The second is that LLMs are prone to xref:hallucination.adoc[*hallucination*] – generating fluent, confident-sounding responses that are factually incorrect – particularly when asked about topics outside their training data or at the edges of their knowledge.

In a RAG system, a user's query is used to search a knowledge base – a xref:vector-database.adoc[*vector database*], a search index, or live web results. The most relevant results are fetched and injected into the model's context alongside the original query. The model then generates a response grounded in that retrieved context, rather than relying solely on what it learned during training.

RAG is widely used to build knowledge-aware applications – internal document Q&A systems, customer support bots, and AI search engines. {link-perplexity}[Perplexity] is a prominent consumer example. It uses live web search to answer questions with cited sources in real time. See xref:ai-assistant.adoc[*AI assistants*] for other examples.

== The pipeline

RAG is a technique, not a framework or a product. Any system that retrieves relevant material and places it in the prompt so the model answers from that data rather than from memory is doing RAG, whatever tools it is built with. Plain RAG is a fixed pipeline with two phases.

In the indexing phase, run ahead of time, source documents are split into *chunks*, each chunk is converted to a vector by an *embedding model*, and the vectors are stored in a vector database alongside the original text and metadata. In the query phase, run on every request, the user's question is embedded with the same model, the nearest chunks are retrieved, and they are inserted into the prompt together with the question. The model then generates its answer from that context. The steps are always the same and always run in the same order: retrieve, then generate. The sequence is decided by code, not by the model.

== Where plain RAG fails

Most of the quality of a RAG system is decided by retrieval, not by generation. If the right passage is not retrieved, the model cannot use it, and it may fill the gap with a plausible guess, which is exactly the hallucination that RAG is meant to prevent. Common causes include:

* *Poor chunking.* Chunks that are too small lose the surrounding meaning, while chunks that are too large dilute the match and waste tokens.

* *Embedding mismatch.* Similarity search finds text that reads like the query, which is not always the text that answers it. Exact identifiers, error codes, and rare terms are often matched better by keyword search, so many systems combine the two in *hybrid search*. See xref:document-search.adoc[*document search*].

* *Weak ranking.* The top-k results by vector distance are not always the best k. A *reranker*, a second model that rescores the candidates against the query, is often added to improve precision.

* *Too much context.* Retrieving generously to avoid missing something fills the context window with marginal material and invites xref:context-rot.adoc[*context rot*].

* *One shot only.* A fixed pipeline retrieves once, with the query as the user wrote it. It cannot notice that the results are irrelevant, reformulate the question, or follow a lead into a second source.

Because each stage can fail independently, RAG systems are evaluated at two levels: whether retrieval returned the right material, and whether the answer was faithful to it. See xref:ai-eval.adoc[*AI eval*].

== Agentic RAG

In *agentic RAG*, retrieval stops being a fixed stage and becomes a tool the xref:agent.adoc[*agent*] can call, one among several alongside others such as a database query, a web search, or code execution. The agent decides when to search, and whether to search at all, since a question that needs no external knowledge needs no retrieval. It rewrites or decomposes the query, tries again with different terms when results are poor, chooses which source to query, and combines what it finds from several sources before answering. This is the xref:agent-loop.adoc[*agent loop*] applied to retrieval, and it is a form of xref:just-in-time-retrieval.adoc[*just-in-time retrieval*].

The trade-off mirrors the one between workflows and agents. Agentic RAG copes with questions that need several lookups or a change of approach, which a single-shot pipeline cannot answer. But each retrieval is another model call, so it costs more and takes longer, and the number of steps varies from one question to the next. It also adds new ways to fail, such as searching too little and answering from memory anyway, or searching repeatedly without converging. Plain RAG remains the better choice for narrow, predictable questions over a single corpus, where its cost, latency, and behavior are all easy to reason about.

Agent development frameworks such as LangChain and LlamaIndex can be used to build RAG capabilities into agents, providing the retrieval, chunking, and orchestration plumbing so developers do not have to wire it together from scratch.
